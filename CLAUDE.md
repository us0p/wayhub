# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mentor: a candidate-focused career platform. The product scope (in Portuguese) is in `SCOPE.md`. The current work is the Phase 1 MVP: Google login, a conversational onboarding interview (real-time voice or text), and per-job CV generation with a fit warning. The implementation plan (10 milestones, with a status table) is in `docs/PLAN.md`; keep its status table current as milestones land.

## Decisions log (mandatory)

`docs/DECISIONS.md` records every product, design and technical decision (D1, D2, …). **Whenever a decision is made or changed with the user, append a new dated row in the same turn.** Never rewrite past rows; mark them `Superseded by Dxx` instead. Read it before making architectural choices: most "why is it like this?" answers are there.

## Commands

The Python toolchain is **uv** with Python 3.12 (`.python-version`). Dependencies are locked in `uv.lock`; use `uv sync --frozen`.

```bash
cp .env.example .env              # first time: fill in generated POSTGRES_PASSWORD / SECRET_KEY (compose refuses to start without them)
# Real Speech/TTS in compose: a git-ignored docker-compose.override.yml mounts the ADC/key file read-only
# at /run/secrets/gcloud-adc.json and sets GOOGLE_APPLICATION_CREDENTIALS to it (D69)
docker compose up                 # db (pgvector pg17) + app (runs migrations, autoreloads on 127.0.0.1:8000) + worker + tailwind --watch
uv run pytest                     # unit + integration (integration needs a *migrated* Postgres at DATABASE_URL — use a separate DB, e.g. mentor_test)
uv run pytest tests/unit/test_home.py::test_home_marks_active_nav_item   # single test
uv run pytest -m e2e --base-url http://localhost:8000 tests/e2e          # Playwright mobile smoke (server *and* `python -m mentor worker` running with fake AI; Chromium gets a fake mic)
uv run pytest -m contract         # real AI provider APIs, opt-in, needs credentials
uv run ruff check . && uv run ruff format --check . && uv run mypy      # same gates as CI (mypy is strict)
uv run alembic upgrade head       # migrations; revision files are named YYYYMMDD_<rev>_<slug>.py
uv run alembic revision --autogenerate --rev-id 0003 -m "..."   # then review: enum drops in downgrade, server defaults
uv run alembic check              # CI fails if models and migrations drift
uv run python -m mentor show EMAIL | set-plan EMAIL tester | set-quota EMAIL job_import {N|unlimited|default}   # admin CLI
uv run python -m mentor worker    # the Procrastinate task worker (compose runs it as `worker`)
```

`addopts` excludes the `contract` and `e2e` markers by default. Passing `-m e2e` or `-m contract` overrides that.

CSS is built with the **Tailwind v4 standalone CLI** (no Node): `tailwindcss -i src/mentor/web/static/css/input.css -o src/mentor/web/static/css/app.css`. `app.css` is git-ignored and built by the Dockerfile `css` stage, the compose `tailwind` service, and CI.

CI (`.github/workflows/ci.yml`) runs these jobs: secrets-scan (gitleaks over full history), lint (ruff + mypy), test (pgvector service; migrations up/down/up, then pytest), e2e (Playwright), and docker build. `.github/workflows/deploy.yml` (D90) runs after CI passes on a push to `main`: it pushes the `mentor`/`mentor-worker` images tagged with the commit SHA to GHCR and runs `deploy.sh <sha>` on the notebook over SSH through Cloudflare Access.

Production (D84, D88, D89) runs on the owner's notebook from `deploy/`: `compose.prod.yml` (installed by hand as `/opt/mentor/compose.yaml`), `deploy.sh <sha>` (pull → migrate → up → `/health`, rollback without migrating, so a migration must stay compatible with the previous release), `.env.prod.example`, and `egress.sh` (blocks the containers from the LAN). The owner's setup checklist is `docs/SETUP_PRODUCAO.md` (pt-BR).

## Security conventions (D36, D37)
- No credential or secret is ever committed, including dev/CI ones: compose reads them from the git-ignored `.env`, CI's throwaway Postgres uses trust auth, and CI generates a per-run `SECRET_KEY`. gitleaks runs in pre-commit and CI.
- Third-party GitHub Actions are pinned to commit SHAs (with a `# vX.Y.Z` comment). Downloaded binaries (Tailwind, gitleaks) are checksum-verified, and CDN scripts carry SRI `integrity`. Bumping a version means updating its hash too.
- `security.py` sets the CSP and other headers on every response. The CSP has no `'unsafe-inline'`/`'unsafe-eval'`: no inline `<script>`, `style=""` or `hx-on` (small behaviors live in `static/js/app.js`: Enter-to-send and the `data-confirm` delete modal). htmx is configured to not inject inline styles. A new external origin (e.g. a CDN) must be added to the CSP deliberately. The e2e smoke test fails on any console error, including CSP violations.
- Published compose ports are bound to `127.0.0.1`.
- HSTS is sent by the app in prod (`SecurityHeadersMiddleware(hsts=...)`), for its own host only (D84).

## Architecture

- `src/mentor/main.py`: the `create_app()` factory (run with `uvicorn --factory mentor.main:create_app`) wires middleware, routers and the exception handlers that turn `LoginRequiredError`/`ConsentRequiredError` into redirects and `QuotaExceededError` into a 429 partial. The dev-login router is only included when `APP_ENV` is dev/test.
- `settings.py`: pydantic-settings loaded from env/`.env`. `get_settings()` is cached (tests that change env use the `fresh_settings` fixture). In prod, Google login credentials, `PRIVACY_CONTACT_EMAIL` and the selected AI providers' credentials are required, and `fake` AI adapters are refused. Secrets are `SecretStr` with **no defaults** (`DATABASE_URL`, `SECRET_KEY` ≥32 chars), and `APP_ENV` defaults to `prod`. Use `settings.database_dsn` for the plain URL.
- `db.py`: async SQLAlchemy engine/sessionmaker and declarative `Base`. Models live in each feature package (`auth/models.py`, `quotas/models.py`, `interview/models.py`, `profile/models.py`); register new model modules in `db.import_models()` or Alembic won't see them. Every user-owned table needs `ForeignKey("users.id", ondelete="CASCADE")`, since account deletion relies on it (D21).
- Auth (`auth/`): route signatures pick a dependency alias from `auth/deps.py`: `CurrentUser` (logged in **and** consented, the default for app pages), `AuthenticatedUser` (no consent needed) or `OptionalUser`. Sessions are opaque cookie tokens, stored hashed (`auth/sessions.py`). State-changing UI actions must be `hx-post`/`hx-delete`, so htmx sends the CSRF header that `auth/csrf.py` enforces; a plain `<form method=post>` will get a 403. Redirect with `web/redirects.redirect()` (it handles htmx) and pass user-supplied targets through `safe_next()`.
- Quotas (`quotas/service.py`, D85): every limit is a **lifetime total** per account, never reset. Call `quotas.check(db, user, kind, amount)` before a costly action and `quotas.record(...)` after it succeeds, **in the same transaction**: `check` takes a per-user advisory lock held until commit. Limits per plan are in `PLAN_LIMITS`, overrides in `user.quota_override` (the admin CLI's `set-quota`, the only way to give more for now).
- Legal (`legal/`): bump `TERMS_VERSION`/`PRIVACY_VERSION` when the text changes in substance; every user is then asked to consent again.
- AI (`ai/`, D45/D46/D55): text and embeddings use **LangChain**. `ai/ports.py` defines the `ChatModels` factory (`chat(effort=...)` → a chat model runnable, `structured(Schema, effort=...)` → a runnable returning the pydantic model), `Effort`, our STT/TTS ports and `AIError` subclasses. Routes take the `AIServices` dependency (`ai/registry.py`; elsewhere `get_ai()`), whose `chat`/`embeddings`/`stt`/`tts` come from `AI_LLM`/`AI_EMBEDDER`/`AI_STT`/`AI_TTS`: `adapters/gemini.py` (`ChatGoogleGenerativeAI` with retries + `with_fallbacks`, normalized `GoogleGenerativeAIEmbeddings`), `adapters/google_speech.py` or `adapters/fake.py`. Tests always run with fakes (forced in `tests/conftest.py`): the `fake_ai` fixture's `fake_ai.chat.script(...)` scripts text/stream replies, `.script_for(Schema, ...)` scripts structured replies per schema, `.calls` records every call (messages, schema, effort). Adding a provider = new adapter + registry branch + contract test in `tests/contract/` (skips without credentials).
- Agents (`agents/`, D54/D56): agents are **LangGraph** graphs. State is checkpointed in Postgres (`agents/checkpoint.py`: `AsyncPostgresSaver` created at app startup in the lifespan (D59: its `setup()` runs `CREATE INDEX CONCURRENTLY`, which would deadlock against a request's open session if run lazily), `Checkpointer` dependency, its tables excluded from Alembic), one thread per interview. Checkpoints don't cascade from `users`: anything deleting user data must also call `delete_threads()`. Integration tests inject an `InMemorySaver` (`checkpointer` fixture).
- Interview (`interview/`, D47/D50/D54/D57): `InterviewEngine` (`engine.py`) owns the lifecycle and our transcript tables and runs the graph in `agent.py` per user turn: `plan` (structured `TurnPlan`, private reasoning) → `speak` (streams the user-facing message from the plan's brief only; never give it the checklist or profile) ∥ `extract` (`ProfilePatch`) → `apply`. The engine forwards only `speak` tokens and yields `ReplyChunk`s then `ReplyDone`/`ReplyFailed` (transport-agnostic, reused by voice in M6). Each user turn gets at most `MAX_REPLY_ATTEMPTS` generations (D58). Routes get the engine through the `Engine` dependency. Prompts live in `prompts.py` (bump `VERSION` on substantive changes); DB helpers in `store.py`; checklist items in `checklist.py`. Routes stream the reply as SSE with heartbeats. Profile facts (`profile/models.py`) carry `source_turn_id` (NULL for facts the user typed); the review screen is `profile/routes.py` + `profile/edit.py` (edit/delete only, no manual adding, D61; parsers, validation, `KINDS` registry; one htmx card/form template pair per kind under `templates/profile/items/`). The interviewer is Mari; a completed interview closes the chat and redirects to `/perfil`, and the single "Adicionar ou alterar detalhes" button reopens it as a follow-up, and the account page is `account/routes.py` (D60); `profile/service.py` renders the profile with short refs and applies patches; `profile/skills.py` normalizes skills (D49).
- Voice (`voice/`, D62–D76): `VoiceSession` (`session.py`) is the transport-agnostic pipeline (STT with stream rotation → end-of-turn → `InterviewEngine` → `SentenceSplitter` → TTS, deaf to the mic while the agent speaks (D71, no barge-in), voice-second metering, `EndReason`s that fall back to text); STT/TTS connection failures are retried 3x with a `notice` toast event before falling back to text (`?voz=connection`, D73/D75); a reply that fails before any text is generated again within the engine's attempts (D76), otherwise `?voz=failure`; the engine's DB session lives for the whole voice session, so reads that feed prompts must not trust objects already in the identity map (`snapshot()` uses `populate_existing`, D76); `routes.py` is the `/entrevista/voz` WebSocket (Origin + cookie + consent checked there, since the CSRF middleware only sees HTTP) and maps events to JSON. The engine's DB session is shared, so every DB access in the session holds its `_db` lock, and short writes are shielded from cancellation. Noise handling (D67/D68): STT denoiser (`GOOGLE_STT_DENOISE`), filler-only finals dropped (`spoken_words`), end of turn waits `end_of_turn_seconds` after a finished sentence and `unfinished_turn_seconds` after one cut mid-sentence; the client's `static/js/noise.js` shows a noisy-room tip. Client: `static/js/voice.js` + the `pcm-capture.js` AudioWorklet; voice UI strings live as data attributes/hidden elements in `components/chat.html` (`voice_panel`, `voice_notices`). Tests: `WebSocketClient` in `tests/integration/helpers.py`; set `VoiceSession.end_of_turn_seconds` etc. with monkeypatch; script `fake_ai.stt.transcripts` (shared across rotated streams; an `Exception` item raises) and `fake_ai.tts.error`.
- Worker (`worker.py`, D28/D78): Procrastinate on Postgres. `worker.app` has no connection settings; `worker.opened()` gives it a pool (the web lifespan opens it only to queue tasks; `python -m mentor worker` runs them). Tasks live in their feature (`jobs/tasks.py`, listed in `import_paths`) and stay thin: open a session and call a service function that tests run directly. Procrastinate's schema is Alembic revision 0005 (vendored `migrations/sql/procrastinate_<version>_schema.sql`; its tables are excluded from autogenerate); upgrading Procrastinate means a new revision with its migration SQL.
- Jobs (`jobs/`, M7, D78/D79): `/vagas/nova` takes one field (a lone URL = link, else pasted text) plus up to 5 screenshots or 1 PDF; `service.submit` validates everything before writing, counts the `job_import` quota and the route queues it (`Queue` dependency; tests override `get_job_queue` and call `service.process` themselves). `service.process` (idempotent) gets the text via `sources.py` (PDF text layer, else one model call transcribing the images/scanned PDF) or `fetch.py` (SSRF-guarded download pinned to the checked IP, trafilatura, Playwright fallback), extracts `ParsedJob` with the posting wrapped as untrusted data (`prompts.py`), stores `JobPosting` + `JobRequirement`s and deletes `job_uploads` (D29). Outcomes are statuses (`ready`, `needs_manual` + reason code, `not_a_job`, `failed`); the job page polls `/vagas/{id}/estado` while queued/processing. Postings are read-only in M7 (view, delete).
- Fit (`fit/`, M8, D80): `fit.service.analyze` runs right after `jobs.service.process` in the `import_job` task (and as `analyze_fit` when the user redoes it). `years.py` computes years from experience dates in Python; one structured `FitJudgement` call judges every requirement (refs R1…, profile rendered with `render(snap, contact=False)`); `met`/`partial` without evidence refs of this profile become `unknown`. One `FitReport` per posting (latest) with `FitItem`s; `digest()` of the profile marks it stale. The job page renders the `jobs/_fit.html` summary card (polls `/vagas/{id}/compatibilidade` while pending), then the CV block `_cvs.html`, then `_requirements.html` (D82); the poll's final answer swaps the last two in out of band. `POST` there redoes it only when stale/failed/lost. Tests: `fake_ai.chat.script_for(FitJudgement, ...)`, `service.analyze(..., today=...)`.
- CV (`cv/`, M9, D81): the job page's `jobs/_cvs.html` posts `/vagas/{id}/curriculos` (D16 lock, `cv_generation` quota, language) → `cv.service.request` creates the next version → `generate_cv` task → `service.generate`: `facts.py` gives the profile citable refs (adds B for bullets and P1), the generator (`GeneratedCV`) writes only sentences with refs, `_Assembler` copies names/companies/dates/contact/skill names from the profile and drops sentences citing nothing, the verifier (`Verification`) sees each sentence with only its cited facts. `cvs.content` is a `CVContent`, `cvs.changes` the shown `Change`s. `render.py` renders the page context, PDF (`cv/print.html`, WeasyPrint, inline styles: never served) and DOCX from the same content, on download, always through `CVContent.visible()`. The editor (M9b, D83: `edit.py`, `/curriculos/{id}/editar`, `cv/_edit_block.html`) addresses items by path (`experiences.0.bullets.2`), edits text (`user_edited`, not verified) and hides items (`hidden`) in the open version; each block swaps itself with htmx. Tests script `GeneratedCV` and `Verification`.
- Logging (`logs.py`): `configure(settings.log_level)` in the app and the worker; our loggers and Procrastinate's at `LOG_LEVEL`, other libraries from WARNING, on stdout.
- Lost tasks (M10): `JobPosting.lost`/`CV.lost` (still waiting `LOST_AFTER` after `requested_at`) stop the polling and offer "Tentar de novo" (`POST .../tentar-novamente`), which bumps `requested_at` and requeues, unmetered; queueing an already queued task is a no-op.
- Logging AI failures: use `mentor.ai.errors.describe(exc)` (types + code locations). Never log provider, LangChain or pydantic exception messages or tracebacks with messages: they can contain the model's output or the user's words (D58).
- Tests: `tests/integration` runs each test in a rolled-back transaction (`db`, `client` fixtures), with login helpers in `tests/integration/helpers.py`. Scope assertions to the test's own user, never to whole-table counts. No inline `style=`, `<script>` or `hx-on` in templates (the CSP blocks them, and a unit test checks).
- `web/`: the Jinja2 environment with `jinja2.ext.i18n`. The UI is **pt-BR only**, but every user-facing string goes through `_()` (D3). Gettext is installed **newstyle**, so a literal `%` in a string must be written `%%`, and values are passed as kwargs: `_("Perfil %(p)s%% completo", p=0)`.
- Templates: **mobile-first, always responsive to desktop (D38)**. Write the phone layout first, then adapt it with `md:`/`lg:` classes; never ship a screen that only works on one size. `base.html` renders both navs from `components/nav.html`: `bottom_nav` (dock + center FAB, `md:hidden`) and `top_nav` (hidden below `md`). Add a nav item to **both** macros. Reusable UI lives in Jinja macros under `templates/components/` (`nav.html`, `cards.html`, `chat.html`); use these instead of re-styling ad hoc. The e2e smoke test runs every page check at 390/768/1440px.
- Design tokens live in the `@theme` block of `static/css/input.css` (palette D4, AA shades D33). `taupe` (#93827F) is decorative only; use `taupe-strong` for muted text. Text on `bg-sage` must be `text-ink`.

### Planned structure (follow it as milestones land)
- CV bullets must cite the source fact IDs, and a verification pass enforces "Model A" (never invent skills or experience).
- Long-running work (job fetch, fit analysis, CV generation) runs as Procrastinate tasks in the `worker` service (see Worker above); PDF/DOCX are rendered on download (D81).
- Quotas are per plan (`free`/`tester`/`admin`) with per-user overrides, lifetime totals (D85): free = 30 voice minutes, 150 text messages, 10 job imports, 10 CVs.
